# Homelab Inventory System — Requirements

## 1. Project Purpose

The Homelab Inventory System is a personal web application intended to help manage and organize hardware owned for a homelab.

The project also serves as a practical learning experience for SQL, Python, database design, and web application development.

## 2. Scope

The initial version will support inventory management for:

- PC components and parts
- Laptops and complete computer systems
- Game consoles
- Mobile devices
- General PC hardware and peripherals
- Networking equipment

Complete systems will be registered as individual inventory items. Loose components can also be registered individually. Tracking the relationship between installed components and complete systems is not currently required.

## 3. Functional Requirements

### Inventory Management

The application shall allow the user to:

- Add inventory items through a browser interface.
- View all registered items.
- View an individual item's information.
- Edit existing inventory records.
- Delete inventory records after confirming the deletion.
- Assign items to existing categories and create new categories when needed.
- Track either individual items or quantities of identical items, depending on the inventory entry.

### Item Information

Each inventory record shall have a unique identifier generated by the system.

The application shall support the following fields:

| Field | Requirement |
|---|---|
| Custom name | Optional |
| Manufacturer | Optional |
| Model | Optional |
| Category | Required |
| Purchase price | Optional |
| Specifications | Optional |
| Working condition | Required |
| Additional notes | Optional |
| Quantity | To be determined during database design |

The working condition shall support four values:

- Working
- Partially working
- Not working
- Untested

Additional notes can describe defects, testing results, or other relevant information.

Specifications should accommodate different types of hardware without requiring every item to have the same technical fields.

### Purchase Price and Cost Tracking

The user shall be able to record the purchase price of an item.

- A price of zero represents an item obtained for free.
- An empty price represents an unknown or unrecorded purchase price.
- The dashboard shall calculate total recorded purchase spending.
- Items with unknown purchase prices shall not be treated as free items.

Estimated current value is a possible future feature and is not part of the confirmed initial scope.

### Inventory Search and Organization

The application shall provide:

- Search by item name, manufacturer, or model.
- Sorting by name, purchase price, manufacturer, or category.
- Filtering by category.
- Filtering by working condition.

### Dashboard

The initial application shall include a dashboard displaying useful inventory summaries.

Planned dashboard information includes:

- Total number of inventory records or items.
- Total recorded purchase spending.
- Breakdown of items by working condition.
- Recently added items.
- A shortcut for adding a new item.

The exact layout will be determined during interface development.

## 4. Technical and Deployment Requirements

The project is intended to use:

- Python for application logic.
- Flask for the web application backend.
- HTML and CSS for the user interface.
- MySQL or MariaDB for relational data storage; the final choice remains undecided.
- Git and GitHub for version control and project hosting.

Development and initial testing will take place locally on the user's Windows PC. The application will subsequently be deployed to the Ubuntu homelab server for occasional testing.

Initial deployment is intended for access over the home network. Remote access may be considered in a future version.

## 5. User and Security Scope

The initial version is intended for a single user.

Multiple accounts, user registration, and role-based permissions are outside the current scope.

The application should avoid unnecessary exposure of the database and should use appropriate access controls and configuration for its deployment environment.

## 6. Development Approach

Development will proceed incrementally:

1. Finalize requirements and database design.
2. Implement the database and test it with sample records.
3. Build the Flask backend.
4. Develop the browser interface.
5. Implement inventory management, search, sorting, filtering, and dashboard functionality.
6. Test locally and resolve issues.
7. Deploy a test version to the Ubuntu server.
8. Update documentation to reflect the implemented system.

## 7. Open Design Decisions

The following details remain to be determined during design:

- How flexible technical specifications will be stored in the database.
- How quantities and purchase prices will work for grouped items.
- The final relational schema, including category relationships.
- Whether estimated current value will be added in a later version.
- The exact dashboard layout.
- The final database engine choice.
